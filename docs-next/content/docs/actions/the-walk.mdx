---
title: The walk
description: Many actions as one correlated route — a plan admitted up front, executed without a model call between steps, answered with a manifest.
---

## Why

A model that returns to its orchestrator between every screen action spends a
round trip per step re-deciding things it already decided. And a batch that
plows ahead blindly is worse: a screen action cannot be rolled back, so
"the batch failed" while the screen sits two steps along is a lie of
summary. The walk is the middle: **admission checks what declarations can
prove before anything runs; execution re-derives every step's offer at its
own turn; and the answer is a manifest** — ran, refused, never-reached, per
row — so partial execution is legible instead of summarized.

The example below uses a fixed local archive and records an open request; it makes no model or
network call. Replace those application functions with the ones your app already owns.

```ts twoslash
import { beginWalk, connectAction, createActionRuntime, defineAction } from 'hcifootprint';
import type { ActionLifecycle } from 'hcifootprint';
const archive = { mostRecent: async (_kind: string) => 'run-42' };
const view = { open: (ref: string) => ({ requestedRun: ref }) };
const runIdSchema = {
  safeParse(value: unknown) {
    return typeof value === 'string' && value.length > 0
      ? { success: true as const, data: value }
      : { success: false as const, error: { issues: [{ message: 'Expected a run id' }] } };
  },
};
// ---cut---

const findRun = defineAction('runs.find', {
  does: 'Find the most recent zone-redundancy run',
  invocation: 'inputless',
  produces: { kind: 'run.ref' },
  settle: { progress: { stages: ['searching', 'found'], required: true } },
  mutate: async (lifecycle?: ActionLifecycle) => {
    lifecycle?.reportProgress('searching');
    const ref = await archive.mostRecent('zone-redundancy');
    lifecycle?.reportProgress('found');
    return ref;
  },
});
const openRun = defineAction('runs.open', {
  does: 'Request that one run opens on screen',
  invocation: 'scalar',
  inputSchema: runIdSchema,
  mutate: (ref: string) => view.open(ref),
});

const runtime = createActionRuntime();
connectAction(runtime, findRun, {
  node: 'runs',
  onInvocation(invocation) {
    invocation.progress?.subscribe(snapshot => console.log(snapshot));
  },
});
connectAction(runtime, openRun, { node: 'runs' });

const walk = beginWalk(runtime, 'agent');
const manifest = await walk.run([
  { action: findRun },
  { action: openRun, carry: { from: 0 } },
], { onRow: row => console.log(row.status) });
// manifest.rows    → [{ status: 'ran', transition }, { status: 'ran', transition }]
// manifest.counts  → { planned: 2, ran: 2, refused: 0, neverReached: 0 }
```

The first action's declared output is carried explicitly into the second action's validated
payload. The progress subscription reports stages inside the first invocation; `onRow` reports
each manifest row as it lands. `ran` rows land after `whenInvoked` settles. Neither requires a model
call between these known steps. A missing offer, ambiguous instance, refusal or failed invocation stops later steps;
the caller can inspect the manifest and replan under the same walk identity.

## Invocation completion and effect truth

`manifest.completed` means every invocation `performed`: the walk awaits `whenInvoked`, not
`whenEffectSettled`. In this example, an open request returning is not proof that the screen
committed or that a business effect succeeded. The transition's effect status and authoritative
settlement remain separate. A closed progress stream is not that settlement either.

Batch steps whose next inputs and availability are known. If the next step depends on a delayed
commit, a fresh observation or a decision nobody owns yet, return to the host/planner or person,
read the actual evidence, and submit the next plan. The walk does not invent a pause/resume
protocol, infer a dependency graph from `needs`, or automatically become a
[Session journey](doc:journeys) served through MCP/WebMCP.

Browser observations can be authoritative evidence when the app's adapter defines and reports
that contract. Merely clicking or seeing a change does not automatically verify the intended
business outcome. The [binding settlement rules](doc:live-bindings)
keep a handler result, execution progress and effect evidence distinct.

## The laws, and why each one

- **An agent may not pre-plan a decision it does not own.** A step whose
  `decisionOwner` the walking principal does not hold is refused at *plan*
  time — not at step three of a half-executed screen. The same step is
  admitted for the owner: the law is ownership, not fear of batching.
- **A carry needs a declared `produces`.** Chaining is what makes plans
  worth having — but free references are a dataflow language by the back
  door. The gate is the declaration: a carried value comes from a declared
  output, never from whatever a handler happened to return.
- **Batched is not blind.** The plan was made from what was true at step
  zero, and step one can invalidate step two — so every step re-reads its
  offers when its turn comes. A guard that stopped holding is a refused row
  carrying the runtime's own teaching sentence.
- **One turn, one walk, many plans.** A refused step means the caller
  replans *under the same walk id*; `walk.record()` then holds the route
  actually taken — which is not the route anybody planned, and comparing
  the two is where the interesting failures live.

Admission failures **throw** before execution. Reached invocation refusals and failures are
recorded in the manifest, with transition refs for steps that ran, so partial execution is not
hidden behind a single success/failure summary.

## Breaking the walk

The human has a door, and the reason travels. A batch a person can watch is
a batch a person must be able to stop — and a break without a reason is a
guard failure wearing a trench coat: the model replans blind, and probably
replans the same thing.

```ts
const walk = beginWalk(runtime, 'agent');
const running = walk.run(steps, {
  onRow: (row) => renderStatus(row),   // the FE's live loop — and where the
});                                     // stop control belongs, beside it

// The person presses stop:
walk.interrupt({ by: 'user', reason: 'wrong array — I meant NORTHWIND-01' });

const manifest = await running;
manifest.interrupted;
// → { by: 'user', reason: 'wrong array — I meant NORTHWIND-01', beforeStep: 1 }
```

The semantics that keep it sound:

- **Step-boundary only.** The current invocation finishes; its effect may still await
  authoritative observation. The walk stops future steps, without cancelling that invocation
  or rolling back a side effect.
- **`interrupted` is a manifest field, not a row status.** Un-run rows stay
  `never-reached`, but the manifest says who stopped it and why — because
  "the plan was wrong" and "the person knows something the plan didn't"
  must be treated completely differently by whoever replans.
- **The walk survives.** A break ends the plan, not the walk: the model
  reads the reason and replans under the same walk id. The break is just
  the most human way a plan ends.
- **The intent stands.** An interrupt armed before a run is consumed at
  step zero — pressing stop between plans is still pressing stop.
